# Security Review — ParkFlows Platform v1 (baseline)
Feature ID: 001 · Reviewer: security-reviewer · Date: 2026-09-25

## Gaps found in inputs
1. **Workflow order not followed.** This review was requested at step 7, but `docs/features/001-parkflows-platform-v1/` holds only `01-prd.md`. There is no `02-ux-design.md`, `03-tech-design.md`, `04-implementation-notes.md`, `05-code-review.md` or `06-test-report.md`, and `review-log.md` shows the PRD still **awaiting user approval**. Gates 1–6 have not been passed.
2. **No feature diff exists.** `git diff --ignore-cr-at-eol` against `main` (d42af6f) shows one real change, 16 lines in `src/App.tsx` (re-fetch after login, and clearing state on logout). The other 26 "modified" files differ only in line endings (CRLF). Because 001 is a *baseline* PRD, I reviewed the **current platform code against the PRD's security-relevant ACs** (AC-01..AC-11, AC-14, AC-20, AC-37, AC-38). Treat this as a pre-launch baseline audit, not a sign-off of a change.
3. **The KNOWN_ISSUES.md entry is out of date on the server side.** The server now has `enforceSiteScope` and `getRequestedSiteId`, so an unscoped list call from a scoped user falls back to their first site. That covers the main AC-02 list paths. The remaining isolation gaps are the ID-based and globally matched paths listed below.
4. **Open questions that affect security:** OQ-3 (strict vs silent scoping), OQ-5 (attendant override), OQ-6 (simulate-attack / clear-history in production) and OQ-11 (retention/deletion of audit data) are unresolved. Findings M1 and L9 depend on them.
5. `npm audit --omit=dev` ran against `package-lock.json`. `node_modules` in the working tree is broken, and there are three stray `node_modules_*` folders in the repo root. Nothing was built or run.

## Scope reviewed
- `server.ts` (every `/api/v1/*` route, auth, CORS/CSRF, site-scoping middleware)
- `src/server/security.ts` (sessions, requireAuth/requirePermission, BOLA guard, rate limits, audit trail, masking, headers)
- `src/server/db.ts` (save/update/entry/exit/valet/registration/role/user functions reached from the routes above)
- `firestore.rules`, `.env.example`, `.gitignore`, `firebase-applet-config.json`
- Client: `src/App.tsx` (the diff), `src/sessionTokenFallback.ts`, `src/components/SiteAdminReports.tsx` (token in URL), `src/mobile/api.ts`, `src/mobile/pinGate.ts`
- Dependencies: `npm audit --omit=dev`

**What's already good (keep it):** Firestore rules deny all client access. Passwords use PBKDF2-SHA512 with 210k iterations and a timing-equalised verify. Login is throttled per IP+identifier and per identifier, with generic error messages. CORS uses an explicit allowlist, and cross-origin state-changing requests are refused. Scoped users cannot claim a foreign `siteId`. Suspended users are rejected on every request (meets AC-10). Reset tokens are single-use and expire after 1 h. Master Admin promotion is guarded. CSV export escapes formula injection. `data/` is git-ignored. The `App.tsx` diff clears the previous user's data on logout, which is an improvement.

| High | H1 `server.ts` `GET /api/v1/logs` (~L1301) | PII masking is controlled by the client. | High | H2 `server.ts` `GET /api/v1/employees/profile` (~L590) + `bolaIdentityGuard` | The guard only inspects `email` / `employeeId`, but the handler also accepts `?query=`. With `?query=<employeeId or plate>` the guard is skipped. Any signed-in user (for example a Gate Attendant) then gets the **full, unmasked** employee record (email, mobile, plate) for anyone in their sites. An ALL_SITES user can do this platform-wide. IDOR, breaks AC-09. | Remove `query`, or run the guard on the resolved employee. Allow only the caller's own record unless the caller has REGISTRATION/APPROVALS view **and** passes the site check. Apply role-based masking to the response. | Open |
| High | H3 `server.ts` `POST /employees/update-vehicle` (~L638) → `db.updateEmployeeVehicle` | The guard and site check key on `email` (the caller's own), but the update matches on `employeeId` **or** email. So `{email: <mine>, employeeId: <victim>}` overwrites another employee's registered plate at **any site**, and that plate is then treated as an authorised employee at the gate. If no match is found, the route also creates a new **ACTIVE** whitelisted employee, skipping pass approval (US-10). | Resolve the target once, from the session user only (non-admins cannot pass an identifier). Enforce the site check on that resolved record. Remove auto-create, or route it into a PENDING registration request. Audit-log the old and new plate. | Open |
| High | H4 `db.saveOrUpdateEmployee` / `db.saveOrUpdateSlot` via `POST /employees/save`, `/employees/bulk-upload`, `/slots/save`, `/slots/bulk-upload` | When the body has `id`, the record is found by id with **no site check**. `enforceSiteScope` only validates the body's `siteId`, which the attacker sets to their own site. A Site Admin (default role has REGISTRATION/INVENTORY edit) can overwrite another customer's employee or slot and move it into their own site. Cross-tenant write and data theft, breaks AC-03. | In the route, load the existing record by id and call `denyForeignSite` on the **stored** `siteId` before saving. Never let a body `siteId` change an existing record's site unless the caller is a Master Admin. Apply the same rule per row in bulk. | Open |
| High | H5 `db.processVehicleExit` via `POST /vehicles/exit`; `db.processVehicleEntry` duplicate check | Exit matches `currentVehicle` **globally**, not per site, so an Attendant at Site A can check out (free the slot, close the log for) a vehicle parked at Site B. The entry "already parked" check is also global and returns the foreign site's slot object. Breaks AC-03 and AC-06. | Scope both lookups to `requestSiteId`. Return 404 for a vehicle parked at a site the caller can't access, without echoing foreign data. | Open |
| High | H6 `server.ts` `GET /api/v1/slots/change-notifications` (~L821) | Not site-scoped and needs no permission. Returns every site's relocation notices, including **plate, employee name and mobile number**, to any signed-in user. | Filter by `getRequestedSiteId`, require `MOBILE_APP` or `FLOOR_PLAN` view, and mask mobile numbers for non-PII roles. | Open |
| High | H7 `server.ts` `GET /api/v1/sites` (~L838) | Returns **every tenant's** site record (contact person, contact email and phone, address, pricing and billing) to any signed-in user, including another customer's Attendants. Cross-tenant disclosure of PII and commercial data, breaks AC-05. | Return only allowed sites to scoped users (reuse the `/my-sites` logic). Strip `contact*` and `pricing` unless the caller has MASTER_CONFIG. | Open |
| High | H8 `POST /rbac/roles` (`db.saveAppRole`), `POST /rbac/users/toggle-module`, `POST /auth/admin/generate-reset-token` | Any holder of USER_MANAGEMENT (delegation is expected by US-22) can: (a) edit **any role**, including their own, to grant MASTER_CONFIG/SECURITY_AUDIT full rights. That leads to clearing audit logs, deleting sites and migrating data. (b) Toggle modules for users at any site. (c) Generate reset tokens for **any non-Master user at any site** and take over that account. `saveAppUser` has site and vertical checks; these three routes don't. Breaks AC-07 and AC-11. | Allow only Master Admins to edit system/default roles and any role granting MASTER_CONFIG, USER_MANAGEMENT or SECURITY_AUDIT. Apply `siteScopeViolation` to toggle-module and reset-token targets. Stop a user from changing their own role or overrides. | Open (latent: the default Site Manager role lacks USER_MANAGEMENT) |
| High | H9 `POST /api/v1/registrations/submit` (public) → `db.submitRegistrationRequest` | Unauthenticated. For any plate already registered, the error returns the **owner's name and employee ID**, so the public can look up who owns a plate (10 req/min/IP, no CAPTCHA). An empty whitelist means *any* email domain is accepted. The domain whitelist is global, not per site (US-13). | Return a generic "cannot register this vehicle, contact your admin" message. Fail closed when a site has no whitelisted domain. Make the whitelist per site. Consider email OTP. | Open |
| Medium | M1 `security.ts` audit trail; `POST /admin/clear-history` | Entries are HMAC'd **individually, not chained**, so deleting or reordering records can't be detected (AC-37/38 require a chain and "name the first broken record"). A Master Admin can wipe `securityAuditLogs`. Verification only checks the in-memory 1,000 entries. Without `AUDIT_HMAC_SECRET`, a hardcoded key in source is used. | Chain each entry's hash to the previous one, persist a sequence number, and verify over Firestore. Refuse to start in production without `AUDIT_HMAC_SECRET`. Remove `securityAuditLogs` from clearable collections, or make audit deletion retention-driven only (OQ-11). | Open |
| Medium | M2 `server.ts` entry/exit/relocation/registration approve+reject/valet/slot save/bulk uploads/domain add+remove/role+user reset | Many security-relevant actions write **no audit event**: vehicle entry/exit, slot change, pass approve/reject, valet status, slot save, slot bulk upload, registration bulk upload with `autoApprove`, domain changes. | Medium | M3 `GET /security/audit-logs`, `/security/compliance-summary`, `/security/verify-audit-chain` | Not site-scoped. Password reset and user edits don't revoke existing sessions. `?token=` on GET puts session tokens in URLs, access logs and browser history (`SiteAdminReports` CSV links). | Destroy the token from any source on logout.
